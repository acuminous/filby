# Changelog

## Unreleased

### Upgrading

Upgrade and restart. Filby applies its own migrations when `init()` is called, regenerates existing aggregate functions with the new ordering and `LANGUAGE sql STABLE` body, relabels existing `POST` frames as `SET`, re-issues change sets that are out of order, records which entities each existing change set touches in `fby_change_set_entity`, records whether each existing entity field is nullable in `fby_entity_field` (key fields are not, every other field is), records the hook event on each existing notification in `fby_notification`, and replaces the default for `fby_change_set.entity_tag` with one that does not use pgcrypto. No other data is changed.

#### More than one frame with the same key in a change set

Entity tables now allow only one frame per key in each change set. If an existing change set breaks this rule, the upgrade stops, nothing is applied, `init()` rejects, and the error names the first duplicate:

```
Entity 'VAT Rate v1' has more than one frame with key (type=standard) in change set '2021 VAT Rates'
HINT: Keep one frame per key in each change set. See the CHANGELOG for a query that lists every duplicate.
```

To list every duplicate for an entity, substitute its table and key columns:

```sql
SELECT cs.id AS change_set_id, cs.description, x.type, COUNT(*) AS frames, MAX(x.fby_frame_id) AS winning_frame_id
FROM vat_rate_v1 x
INNER JOIN fby_data_frame f ON f.id = x.fby_frame_id
INNER JOIN fby_change_set cs ON cs.id = f.change_set_id
GROUP BY cs.id, cs.description, x.type
HAVING COUNT(*) > 1
ORDER BY cs.id;
```

Previously the frame with the highest id won, so you can safely keep that frame and delete the others for the same key and change set. Delete each frame's entity row first, then its `fby_data_frame` row. Filby does not delete your data for you.

#### Change sets that are out of order

If an existing change set has a later effective date than a change set added after it, typically because it was pre-released, the upgrade re-issues it as a new change set, just as adding the later change set would now do. See [Correcting and Re-issuing Data](README.md#correcting-and-re-issuing-data). The change log may therefore gain entries, the originals drop out of it, and `ADD_CHANGE_SET` notifications are scheduled for the re-issued change sets. The originals are still returned by `getChangeSet` and `getAggregates` with their original results (#100).

#### SQL that uses the POST action

The `POST` value of `fby_action_type` is renamed to `SET`. YAML, JSON and CSV migrations that use `POST` keep working, but your own SQL that uses the literal `'POST'` must change to `'SET'`. This includes custom functions, views and raw SQL migrations that insert data frames. Replaying such a raw SQL migration against a fresh database fails, because the value no longer exists.

### Changed

- The example data is replaced by a park and caravan catalogue: ten parks with amenities, seasons, offers and the models they sell, and a catalogue of manufacturers, models, grades, accessories, prices and VAT rates, loaded entirely from CSV by ten change sets running from October 2024 to a 2027 price list that is not yet live. The old parks and seasons gave the reader two kinds of date with nothing to tell them apart and only one entity with any shape; the new data lets the README walkthrough answer questions a product person asks, such as what a park sells, what the catalogue was on a date and which VAT rate applied during the temporary reduced rate of summer 2026. The projections are `Amenities`, `Catalogue`, `Grades`, `Models`, `Parks (Detailed)`, `Parks (Minimal)` and `VAT Rates`, served at `/api/projections/<name>/v1`; the two park projections differ only in whether each park amenity carries the amenity's name, category, age group, charge and VAT code or its code alone, and `Grades` lists the attributes each grade requires and the models that held it each year (#179, #187).
- The example applications are [Hono](https://hono.dev/) applications rather than Fastify ones. Each mounts `filby.fetch` in one line to serve the change log, the projections and the OpenAPI document under `/api`, serves Swagger UI at `/documentation` from the generated `/api/openapi.json` in place of the hand-written `examples/schemas`, and posts webhooks with the global `fetch`. The parks are now at `/api/projections/park/v1` rather than `/api/projection/v1/park`, and the TypeScript example's config is a typed `Config` literal. See [Example Applications](README.md#example-applications) (#65).
- The JavaScript example application is removed. The TypeScript example is the same program, and is the one that compiles against `index.d.ts`, so it is the only one kept (#175).
- Aggregate functions select, for each key, the frame from the change set with the latest effective date rather than the most recently added frame. Previously, backfilling a change set dated before an existing one overrode the later values (#3).
- A change set may contain only one frame per key for each entity, whether the frames set or delete it. Entity tables gain `fby_change_set_id`, `UNIQUE (fby_change_set_id, <key columns>)` replaces the old unique constraint (which could never fail), and key columns are `NOT NULL` (#6).
- Entity tables reference `fby_data_frame` with `ON DELETE CASCADE`, so deleting a change set with SQL also deletes its entity rows. A superseded change set and its re-issue must be deleted in the same statement. See [Correcting and Re-issuing Data](README.md#correcting-and-re-issuing-data) (#6, #25).
- The `POST` frame action is renamed to `SET`, in the DSL and in the database. `POST` is also accepted in YAML, JSON and CSV, and is stored as `SET` (#77).
- Aggregate functions are generated as `LANGUAGE sql STABLE`, so Postgres can inline them and apply the caller's filters before the aggregate is materialised (#36).
- Adding a change set re-issues every live change set with a later effective date as a new change set with the same description, effective date and data frames, and marks the original as superseded, so change set ids always follow effective dates. One migration can therefore add more than one change log entry, and each re-issued change set schedules `ADD_CHANGE_SET` notifications. See [Correcting and Re-issuing Data](README.md#correcting-and-re-issuing-data) (#4).
- `getChangeLog` returns change sets ordered by change set id, oldest first. Previously the order was whatever Postgres happened to return (#19).
- `getChangeLog` and `getCurrentChangeSet` read `fby_change_set_entity`, one row per change set and entity, instead of every data frame, so their cost grows with the number of change sets rather than the number of frames. A trigger on `fby_data_frame` fills the table, so data frames inserted by your own SQL are included. Deleting every data frame for an entity in a change set with SQL does not remove the change set from the change log of projections that use that entity, so delete the change set instead (#38).
- `fby_data_frame` is indexed on `(entity_id, change_set_id)`, so aggregate functions no longer scan every data frame to find an entity's frames up to a change set (#35).
- Filby no longer creates or uses the pgcrypto extension. `init()` previously failed on a database that already had it, and needed the privilege to create extensions, which managed Postgres services often withhold. Entity tags are now derived from `gen_random_uuid()` and keep their 20 hexadecimal character form. Existing entity tags are unchanged, and the extension stays installed but unused by Filby, so drop it if nothing else needs it (#23).
- A projection dependency or change set frame that names an entity which does not exist fails with `Projection 'VAT Rates v1' references a non existent entity 'VAT Rate v2'` or `Change set '2020 VAT Rates' references a non existent entity 'VAT Rate v2'`, instead of a `NOT NULL` violation on `entity_id` (#26).
- The errors for references to a non existent entity or projection end with a hint: `; did you mean 'Park v1'?` when an entity or projection with the same name in a different case and the same version exists, otherwise `; existing entities are 'Park v1', 'Season v1'` or `; no entities exist`. `getAggregates` rejects with `Change set 42 does not exist` when the change set does not exist, instead of returning an empty array (#49).
- An `ADD_HOOK` with a `projection` and `version` must have a change set event, `ADD_CHANGE_SET` or `COMMENCE_CHANGE_SET`. Previously a projection on an `ADD_PROJECTION` or `DROP_PROJECTION` hook was silently ignored and the hook fired for every projection. `DROP_ENTITY` now requires `operation` like every other operation (#29).
- Change set data frames are rendered as JSON in batches of up to 1000 rows and converted by Postgres using the entity table's row type, instead of three statements per row, so a 20,000 row CSV loads in under a second rather than about 30 seconds. A data frame field or CSV column that the entity does not declare fails with `Change set '2020 VAT Rates' references a non existent field 'wombat' of entity 'VAT Rate v1'` instead of a Postgres `column does not exist` error (#37).
- A change set row that Postgres rejects fails with the migration file, the row's location and Postgres's message, for example `0004.season-2020.yaml: /0/frames/1/data/2 - invalid input syntax for type numeric: "abc"` for inline data, using the `changes` or `frames` key as written, or `0004.season-2020.yaml: csv/season-2020.csv:18 - invalid input value for enum season_type: "Owner"` for a CSV source, naming the source as written with the header as line 1. This covers values that cannot be cast to the column type, unknown enum values, missing key fields, check violations and malformed timestamps. The error keeps Postgres's SQLSTATE, and nothing from the migration is applied. Each batch is inserted by a loop with an exception handler per row, which adds about 100 ms per 10,000 rows (#157).
- Notifications pause while migrations run. `init()` holds the exclusive advisory lock `Filby.MIGRATION_LOCK_KEY` (`102105108098121`) for the duration of the migrations, and each poll takes it in shared mode inside the delivery transaction, skipping the poll if it is not granted, so no new delivery starts on any instance until the migrations have finished and a migration waits for deliveries already in flight. `init()` can therefore wait up to the handler timeout for an in-flight delivery of the same hook and projection, so keep `handlerTimeout` short (#101).
- `fby_hook.name` is declared `UNIQUE` rather than `UNIQUE NULLS NOT DISTINCT`. The clause did nothing on a `NOT NULL` column. Existing databases are unchanged (#28).
- Every failed delivery attempt emits `Filby.NOTIFICATION_ERROR` with the attempt's error and the notification, after the failure has been recorded, so a struggling hook is visible before it is exhausted. The `Filby.HOOK_MAX_ATTEMPTS_EXHAUSTED` payload is now the same `{ error, notification }` object instead of `{ ...notification, err }`, and the `ErrorNotification` type is removed. Both events are emitted synchronously and an error thrown by a listener is discarded (#16).

### Fixed

- `getAggregates` quotes the aggregate function name, so an entity whose name contains characters that are not valid in an unquoted identifier can be read through the API as well as through its table (#27).
- Entity field types may contain commas, square brackets and dots, so `NUMERIC(10,2)`, `DECIMAL(5,2)`, `TEXT[]` and schema-qualified types such as `accounts.currency` are accepted. Quotes, semicolons and other characters that could break out of a column definition are still rejected, and the error now names the entity and field (#9).
- `startNotifications` does nothing if Filby is already polling. Previously each call started another poller, and only the last could be stopped, so `stopNotifications` and `stop` left the others running. `stopNotifications` now discards the stopped poller, so `startNotifications` after it starts a fresh one (#21).
- A YAML data frame field with no value (`label:` or `label: ~`) is stored as `NULL`. Previously text columns stored an empty string and other columns failed with a cast error. A nested map or list is stored as JSON, so it can be loaded into a `JSON` or `JSONB` column; a quoted value is still stored as text (#8).
- CSV cells are stored as the text in the file and cast by Postgres to the column type, so `007` keeps its leading zeros in a `TEXT` column and `1.50` keeps its scale in a `NUMERIC` column. Previously cells were converted to JavaScript values first, so `007` became `7`, `1e3` became `1000`, `1.50` became `1.5` and `TRUE` became `true` whatever the column type. An empty CSV cell is stored as `NULL` (#7).
- `unsubscribe(event)` with no handler removes every handler for the event, as documented. Previously it threw `removeListener only takes instances of Function` (#20).
- `withTransaction` runs its callback inside a real transaction, committed when the callback returns and rolled back if it throws, and a client whose transaction failed is discarded rather than returned to the pool. Previously there was no `BEGIN`, so the lock taken when claiming a notification was released before the handler ran and two instances polling the same database could both deliver it. The lock is now held for the whole delivery, so other instances skip the notification and it is delivered once (#13).
- Filby no longer modifies the shared Handlebars module. Its helpers and partials are registered on a private Handlebars environment, and the guard that rejects unescaped expressions is installed only while a Filby migration is rendered. Previously, loading Filby made a host application's own Handlebars templates throw and replaced any helper the host had registered under the same name (#24).
- Passing a notification removes only the previous successful notification for the same hook and projection. Previously it removed every successful notification for the hook, so for a hook that is not restricted to a projection, delivering one projection's notification discarded the record of the last successful delivery for every other projection (#18).
- A failed poll for notifications, such as a database outage, is reported by emitting `Filby.NOTIFICATION_ERROR` with the error, and polling continues at the next interval. Previously the first failed poll stopped polling for good and raised an unhandled rejection, which exits the process under Node's defaults (#14).
- An unparseable `notifications` duration such as `interval: 'soon'` is rejected when Filby is constructed with `Invalid config: /notifications/interval must be a duration such as '30s'`. A negative duration is rejected too. Previously the string passed validation and `parse-duration` turned it into `null` at runtime, so failed hooks were retried with no backoff, handlers were aborted immediately or the poller looped without delay (#134).
- A notification for a hook with no subscriber is treated as a failed attempt, so `last_error` records `No subscribers for hook '...'`, the normal backoff and `HOOK_MAX_ATTEMPTS_EXHAUSTED` apply, and a late subscriber receives it on the next attempt. Previously the notification was marked OK and deleted, so a hook name typo, a case mismatch or calling `startNotifications` before `subscribe` silently lost events (#15).
- An error raised by the connection pool, such as the server closing an idle connection after a restart or failover, is reported by emitting `Filby.NOTIFICATION_ERROR` with the error. Previously the pool had no error listener, so the `error` event was unhandled and exited the process (#17).
- `DROP_ENUM` and `ALTER_ENUM` look the enum up by its canonical name, so an enum added as `Season Type` can be dropped, and can have values added, by that name. Previously `ADD_ENUM` created the type as `season_type` but the other two operations looked for a type named `Season Type` and failed with `Enum 'Season Type' does not exist`. The error for an enum that really does not exist still quotes the name as written (#145).
- A `Filby.HOOK_MAX_ATTEMPTS_EXHAUSTED` listener that throws no longer takes the process down. The failed attempt stays recorded and polling continues. Previously the emit was not awaited, so a rejecting listener raised an unhandled rejection, which exits the process under Node's defaults (#16).
- A CSV source with a single column loads. papaparse cannot detect a delimiter in a file that contains none and reports that as an error, which Filby treated as fatal, so a DELETE frame whose CSV holds only the key column failed with `Unable to auto-detect delimiting character`. CSV sources are now always read as comma separated (#152).
- `index.d.ts` matches the code: `Projection` has `id`, `Notification.projection` is typed without it because notifications record the projection name and version, `getProjection`, `getChangeSet` and `getCurrentChangeSet` return `| undefined`, `subscribe`, `unsubscribe` and `unsubscribeAll` return `void`, and the `config` getter is declared (#31).

### Added

- `notifications.listen: true` wakes the poller as soon as a notification is scheduled. Filby holds a dedicated connection that `LISTEN`s on the `fby_notification` channel, which `fby_schedule_notification` now notifies, and polls immediately on each message, so `ADD_CHANGE_SET`, `ADD_PROJECTION` and `DROP_PROJECTION` are delivered within a second instead of up to one interval later. `init()` also notifies once the migration lock is released, so other instances are woken when a migration completes rather than while it still holds the lock. Polling remains the safety net: if the listening connection drops, the error is emitted as `Filby.NOTIFICATION_ERROR`, Filby reconnects with exponential backoff from one second up to one minute, and anything notified in the meantime is delivered by the next poll. `COMMENCE_CHANGE_SET` is always delivered by the poll, since a change set reaching its effective date is not a database write. See [Configuration](README.md#configuration) (#57).
- The DSL gains equivalent forms: entity `fields` as a map (`code: TEXT`, or `price:` with `type` and `nullable`), `key` for `identified_by`, `changes` for `frames`, and `entity: park@1` or `projection: parks@1` for the `entity` or `projection` plus `version` pair. `version` defaults to 1 on `ADD_ENTITY` and `ADD_PROJECTION`, but never on a reference. Every existing spelling remains a first-class equivalent and old migrations run unchanged. See [Equivalent forms](README.md#equivalent-forms) (#51).
- Entity fields can be declared `nullable: false`. `fby_entity_field` gains `nullable`, recorded from the declaration (key fields are never nullable) and backfilled as `false` for key fields and `true` for every other existing field. Nullability is not yet enforced on the entity table, because a `DELETE` frame carries only the key fields (#51).
- Entity definitions are recorded in `fby_entity_field`, `fby_entity_check` and `fby_enum`. Existing entities and enums are backfilled on upgrade (#3).
- `fby_change_set` gains `superseded_by` and `reissued_from`. `getChangeLog` and `getCurrentChangeSet` exclude change sets whose `superseded_by` is set, while `getChangeSet` still returns them. Change sets gain `reissuedFrom`, the id of the change set they re-issue, if any. (#99).
- `getChangeLog` accepts `{ since: changeSetId }` and returns only the change sets with a higher id, so a consumer can resume from the last change set it processed (#56).
- A change set's `effective` may be a calendar date, such as `2026-01-01`, when the change set declares a `timezone` (an IANA name such as `Europe/London`). The date is midnight in that timezone, so daylight saving time is handled by Postgres. A bare date without a `timezone` is rejected, because Filby never uses the process timezone. Timestamps with an explicit offset work as before, with or without a `timezone`. YAML parsing is pinned to the YAML 1.2 core schema, so a bare date is always read as a string (#102).
- A `COMMENCE_CHANGE_SET` hook event, declared like `ADD_CHANGE_SET` with an optional projection, fires when a projection's current change set changes: immediately for a change set whose effective date has already passed, and on the effective date for a pre-released one, so a consumer caching current data hears about next year's rates when they take effect. The notification is scheduled when the change set is added, so it survives restarts, and a re-issued change set schedules one for its inherited effective date. Each pre-released effective date fires once, whereas `ADD_CHANGE_SET` notifications for a projection still coalesce into one. `fby_notification` gains an `event` column, and `fby_notify_add_change_set` now takes the change set id as its first argument, which only affects your own SQL that calls it. See [Notifications](README.md#notification) (#55).
- Notification handlers receive `{ signal }` as a second argument, an `AbortSignal` that is aborted when the handler exceeds `notifications.handlerTimeout` (default `30s`) or when `stopNotifications` or `stop` is called. A handler that times out is treated as a failed attempt, so the normal backoff and `HOOK_MAX_ATTEMPTS_EXHAUSTED` apply, and `last_error` records the timeout. Previously a hung handler blocked the poller for ever and, since #13, held the notification's row lock. A timed-out handler may still complete later, so handlers must be idempotent. See [filby.subscribe](README.md#filbysubscribetevent-string-handler-notification-t-context-handlercontext--promisevoid-void) (#22).
- Frame actions are matched case-insensitively, in YAML, JSON and CSV, so `set`, `Delete` and `post` are accepted and stored upper case. A source frame may specify an `action`, which applies to every row of its CSV, and the CSV must then have no `action` column. A source frame without an `action` requires the CSV to have an `action` column with every cell filled; an empty cell fails the migration with `Error parsing <file>:<row> - Missing action`. Inline frames still require an `action` (#103).
- `getNotificationStatus()` reports whether Filby is polling, whether the poller is `idle` or `running`, the time of the last successful poll, the number of failed polls since then and the last error, and the number of pending, overdue and exhausted notifications, for health checks. The example applications expose it at `GET /health`. See [filby.getNotificationStatus](README.md#filbygetnotificationstatus-promisenotificationstatus) (#58).
- An `ALTER_ENUM` operation adds values to an existing enum, after its current values and in the order listed, and records them in `fby_enum`. Adding a value the enum already has, or altering an enum that does not exist, fails with a readable error. A change set that uses a new value belongs in a later migration file, because Postgres cannot use a new enum value in the transaction that added it; using it in the same file fails with Postgres's `unsafe use of new value` error. See [Data Definition](README.md#data-definition) (#62).
- A command line tool. `npx filby validate [directory ...]` parses, schema-validates and renders every migration in the given directories (`migrations` by default) without a database, reads the CSV files that `source` frames refer to, reports every failure as `<file>: <message>` with the JSON path, and exits 1 if any migration failed. `npx filby preview [directory ...]` performs the same checks and prints the SQL that `filby.init()` would run, in order, each migration preceded by a `-- <file>` comment. See [Command Line](README.md#command-line) (#47).
- The migration schema is published at https://acuminous.github.io/filby/lib/schema.json and declares it as its `$id`. A YAML migration that starts with `# yaml-language-server: $schema=https://acuminous.github.io/filby/lib/schema.json` is validated and completed as you type by any editor with YAML language server support, such as VS Code with the YAML extension. The example migrations and README examples carry the comment. See [Data Definition](README.md#data-definition) (#48).
- `ADD_PROJECTION` accepts a `root` entity reference in place of `dependencies`, and Filby generates the projection function. `get_<name>_v<version>(p_change_set_id, ...)` returns one row per root entity, with the root's columns, selected from the entity's aggregate function as `LANGUAGE sql STABLE`. `parameters` map a name to a root `field` and a `match` operator (`equals` by default, `prefix`, `in` or `range`), each becoming a nullable argument, `p_<name>`, or `p_<name>_from` and `p_<name>_to` for a range, that filters the rows when supplied; `prefix` matches literally, so `%` and `_` are not wildcards. `order` lists root fields to sort by, each with an optional `direction` (`ASC` by default, or `DESC`) and `nulls` (`FIRST` or `LAST`), with the entity key appended ascending as a tie break and used alone when no order is declared. `paging` declares a default `page_size` and a server `page_max`, adding `p_page_offset` and `p_page_size` arguments, clamped to `page_max`, and an `fby_total` column with the number of rows that matched; `change_set_id`, `page_offset` and `page_size` are reserved parameter names. The root is recorded as the projection's dependency, and the declaration in `fby_projection.root_entity_id`, `page_size` and `page_max`, `fby_projection_parameter` and `fby_projection_order`. A parameter or order on a field the root does not have, `root` together with `dependencies`, or `parameters`, `order` or `paging` without `root` fails the migration. `DROP_PROJECTION` drops the generated function; hand-written projections keep declaring `dependencies` and their functions are left alone. See [Data Definition](README.md#data-definition) (#63).
- A root projection may `nest` child entities, and `filby.getDocuments(projection, changeSetId, { parameters, pageOffset, pageSize })` assembles the documents. Each entry names a child `entity`, an `on` map from the child's field to its parent's field, and an optional `order` in the same form as the root's, with the child's key appended ascending, and may itself contain a `nest` block, to any depth, so `park` can nest `seasons` which nest `rates`. The generated function is unchanged by `nest`; `getDocuments` calls it, then runs one query per nest at any depth, semi-joining the child aggregate through its ancestors to the same root rows, and returns `{ documents, total }`, each document being a root row with one array property per entry, named by its key, holding every child field except the join fields, in the declared order, or an empty array for a parent with no children, and each nested document carrying its own nests in turn. Paging applies to the root rows, so a page is N roots with everything under them and `total` counts roots. Nested values pass through node-pg exactly as root values do, so a timestamp is a `Date` at every level. `getDocuments` rejects a projection declared with `dependencies` and an unknown parameter. Every nested entity at every depth is recorded as a dependency of the projection, so a change set for a child or grandchild notifies the projection's hooks, and the declaration is recorded in `fby_projection_nest` (with `parent_nest_id`), `fby_projection_nest_on` and `fby_projection_nest_order`. A nest on a missing entity, a join or order on a field the entity does not have, a nest named after a field of its parent entity or `fby_total`, the same canonical nest name twice under one parent, or `nest` without `root` fails the migration with a message naming the nest path, such as `nest 'seasons.rates'`. The per-parent uniqueness of nest names uses `UNIQUE NULLS NOT DISTINCT`, so Filby requires PostgreSQL 15 or later. The example application's hand-written `get_park_v1` is replaced by a nested projection and the routes call `getDocuments`. See [Data Definition](README.md#data-definition) and [filby.getDocuments](README.md#filbygetdocumentstprojection-projection-changesetid-number-options-documentoptions-promisedocumentst) (#104, #163, #177).
- Projection parameters accept four comparison operators: `gt`, `gte`, `lt` and `lte`. Each becomes a single nullable argument, `p_<name>`, of the field's type, and filters the rows with `>`, `>=`, `<` or `<=` when supplied, so a strict bound no longer needs a `range` nudged past the boundary row. Two parameters may name the same field, so `gt` and `lte` on one field make a half-open interval, which suits cursor-style paging. `range` is unchanged and parameters still combine with AND. See [Data Definition](README.md#data-definition) (#161).
- `filby.fetch(request, { basePath })` serves projections and change logs over HTTP with the web standard `Request` and `Response`, so Hono mounts it in one line and Express or Fastify adapt it in a few. `GET /changelog?projection=<name>&version=<n>[&since=<id>]` returns the change log with `ETag` and `Last-Modified` from the latest entry. `GET /projections/<name>/v<n>` redirects to the same URL with the current `changeSetId`, or is a 404 when there is none. `GET /projections/<name>/v<n>?changeSetId=<id>` returns a projection's documents as a JSON array, filtered by its declared parameters under the names `getDocuments` accepts (an `in` parameter repeated, `?types=a&types=b`), paged with a 1-based `page` and a `pageSize` clamped to `page_max`, with `ETag`, `Last-Modified`, `Cache-Control: max-age=31536000, immutable`, `X-Total-Count` and `Link` headers for the next and previous pages. A projection declared with `dependencies` is served by calling its function and returning the rows, paged by row when `pageSize` is given. An unknown change set, an undeclared or malformed query parameter, or a value Postgres cannot convert is a 400; an unknown projection, path or current change set is a 404; a method other than `GET` is a 405; errors are JSON `{ error }`. See [filby.fetch](README.md#filbyfetchrequest-request-options-fetchoptions-promiseresponse) (#59).
- `GET /openapi.json` on `filby.fetch` returns an OpenAPI 3.1 document generated from the metadata tables: the `/changelog` path and one path per projection with its declared parameters, its paging parameters and a response schema derived from the root entity's fields and the nesting, so a new projection is documented without anyone writing a schema. `FetchOptions.info` sets the document's `info` (default `{ title: 'Filby', version: '1.0.0' }`) and `basePath` becomes its `servers` entry. Field types describe what node-pg emits, so `NUMERIC` and `BIGINT` are strings and `DATE` and `TIMESTAMP` are `date-time` strings; a projection declared with `dependencies` has an unconstrained response because Filby does not know the shape of its function. See [filby.fetch](README.md#filbyfetchrequest-request-options-fetchoptions-promiseresponse) (#64).
- `filby.fetch` serves `GET /projections`, a JSON array of `{ name, version, description }` for every projection in name and version order, `description` null when none was declared, without cache headers because the list changes when a projection is added or dropped. The OpenAPI document gains the `/projections` path and a `Projection` schema. See [filby.fetch](README.md#filbyfetchrequest-request-options-fetchoptions-promiseresponse) (#180).
